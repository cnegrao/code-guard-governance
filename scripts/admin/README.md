# Existing-organisation operator invitation

This administrative entry point onboards a real operator into an existing
organisation, without using public signup or transferring another user's
membership. The current CLI deliberately accepts only `ov-ia-g2-test`
(`zkqfvqwqdypgpzauzinw`). It is not a production provisioning command.

Prerequisites: Node 24, the installed/authenticated Supabase CLI, the additive
`20261108002618_governance_operator_invitation_v1.sql` migration already applied,
and an explicitly authorised real operator name/email and organisation.

From the isolated E1 worktree, using its test project link:

```powershell
$env:NODE_USE_SYSTEM_CA='1'
node scripts/admin/issue-operator-invitation.mjs `
  --project-ref zkqfvqwqdypgpzauzinw `
  --org-id 082ef694-e016-4893-908c-1eef373f53af `
  --org-code GOVIA_DEMO `
  --email negrao@ia4all.eu `
  --name 'Carlos Negrão' `
  --reason 'Owner-authorised onboarding of the real E1 operator.' `
  --hours 2
```

The command checks the linked project before connecting. The database checks
the supplied organisation UUID/code, active status, absence of an existing email
and the actual system `GOVERNANCE_ADMIN` role. Only the database administrator
can issue invitations. Reissue revokes prior outstanding invitations for the same
email in the same organisation. It cannot transfer an existing account or replace
another organisation's pending invitation.

The random 256-bit code is saved to `activation-code.txt` under a newly created
private `.artifacts/agent/operator-invitations/<local-id>` directory. On Windows,
the directory permits only the current OS user and SYSTEM; on POSIX it uses 0700
and 0600. The code is never printed or placed in a URL. Its SHA256 digest, bounded
expiry and immutable administrative identity/role receipt are stored in the DB.
No password or authenticated session is generated by this command. Do not send
the private code through logs, source control or shared reports.

The operator opens `http://localhost:3101/accept-invitation`, enters the privately
delivered code, verifies the prebound identity/organisation/role and chooses a
password. The server hashes it with the existing bcrypt cost 12. A single DB
transaction creates the governance user and consumes the invitation. The existing
ALWAYS credential trigger authors the exact credential epoch. Expiry, one-use,
current organisation/role validity and email uniqueness are checked at redemption.

The operator then uses the existing `/login` form. Activation never signs a
session. Normal login verifies the credential and persisted organisation/role,
and existing governance write boundaries independently enforce current authority.
No Supabase Auth account is created and no review decision is made.

For E1, use `http://localhost:3101` consistently for login and review. Host-only
cookies are not shared with 127.0.0.1. The local middleware redirects loopback
alias navigation before login; submitting credentials to the old alias is refused.
The test dashboard launcher reuses its signing configuration from a restricted
private runtime file, with no key value printed or passed as a command argument.

Public API requests carry only the code and optionally the chosen password;
caller-selected email, organisation and role are rejected. The endpoint checks
the configured Origin and incoming Host, permits HTTPS or explicit loopback HTTP,
does not cache responses and does not log credentials or codes. Issuance is not
exposed through a public endpoint. All four new DB routines are SECURITY INVOKER;
there is no addition to the application SECURITY DEFINER capability surface.

This adds only the invitation mechanism. Human review, certification,
reconciliation and materialization remain separate operator actions.
