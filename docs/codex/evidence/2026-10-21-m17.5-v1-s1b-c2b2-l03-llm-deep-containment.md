## Old and new contract

Removed `ComplianceIssue`, `FrameworkAuditResult`, `ConsolidatedAuditResult`,
`status_overall`, `overall_status` and their framework attainment semantics.
No compatible status alias, global favorable state, score, percentage or hidden
legacy result remains. New public types: `TechnicalFrameworkFinding`,
`FrameworkReviewResult`, `TechnicalFrameworkReviewResult`.

Every consolidated and per-reference result has the application-owned boundary:

```json
{
  "kind": "LLM_ASSISTED_TECHNICAL_FRAMEWORK_REVIEW",
  "authority": "HEURISTIC_NON_AUTHORITATIVE",
  "legal_conclusion": false,
  "compliance_determination": false,
  "framework_satisfaction": false,
  "control_effectiveness": false,
  "certification": false,
  "attestation": false,
  "assurance": false
}
```

The literal object is frozen; model boundary objects are never copied. Negative
type fixtures reject affirmative authority and removed attainment fields in both
runtime and SDK types. Descriptive consolidated counts are requested IDs,
complete-review count (`frameworks_analyzed`), incomplete/unknown-review count
(`frameworks_unknown`), total/high-priority findings and acquired file count.
They do not form a framework score or arithmetic coverage.

| Finding/acquisition semantics | Behavior |
| --- | --- |
| `FINDINGS_DETECTED` | Validated potential source findings with at least one successfully analyzed required batch. May coexist with PARTIAL completeness. |
| `NO_FINDINGS_DETECTED` | Nonzero required batches, every required batch successfully analyzed, declared acquisition complete, zero findings and no recorded uncertainty. Means only absence in the supplied analyzed input. |
| `UNKNOWN` | Complete result could not be established: malformed/unsupported output, missing/empty/model-thrown response, acquisition/context dependency failure or zero successful batches. Provisional validated findings can remain visible separately. |
| `COMPLETE` | Technical execution for all declared batches completed without recorded acquisition uncertainty. Never a complete assessment of a framework/organization. |
| `PARTIAL` | Some batches or provisional findings available, but complete technical review cannot be established. |
| completeness `UNKNOWN` | No successful analysis or usable findings. Zero input/batches never produce a favorable default. |

Results include exact source file names, required/analyzed/failed batch counts,
closed reason enums and batch indices (or `null` for source/dependency scope).
File-read/directory failures are recorded, not silently interpreted as clean
input. Existing ignored/unsupported/large/empty inputs remain explicitly excluded
from scope, and truncation prevents complete absence conclusions.

## Prompt, parser and aggregation containment

Every prompt is a technical code-review assistant, never a legal auditor,
compliance officer or lead auditor. Common instructions forbid legal compliance,
applicability, organization/system satisfaction, pass/fail, certification,
attestation, effectiveness/readiness and authoritative regulatory classification;
they distinguish source evidence from external organizational/legal facts.
Absence cannot imply satisfaction. Human/domain/legal review is explicit.
All templates use the working `{CODE_CONTENT}` placeholder; original spaced
placeholders in several prompts no longer omit the actual supplied code.

LGPD/GDPR keep data-handling topics; ISO technical controls are reference hints
with organizational/people/physical facts outside inference. AI Act legal risk
classification, ANVISA/device legal class and NIS2 entity classification are
removed without replacement regulatory conclusions. MDR/HIPAA/HIPAA remain
health-data/error-handling topics; SOC2 criteria, OWASP categories, PSD2,
BACEN/CVM, FAPI-BR and PIX remain engineering considerations only. CCPA, PCI_DSS,
CRA, DORA and MDR previously lacked dedicated map entries and fell back to GDPR;
their current generic prompts preserve their exact selected identifiers and
explicitly disclaim framework-specific interpretation. No new legal substance.

The parser validates object/framework/state/array, required finding strings,
closed engineering severity and positive in-range source lines in actual batch
files. It constructs only allowlisted finding fields. Unsupported shapes or
state/finding inconsistencies yield sanitized reason enums and no fake source
finding. Markdown fencing is supported only around a complete JSON result.
Legacy-only pass output is UNKNOWN. Extra `status_overall`, `overall_status`,
`compliant`, `certified`, alignment, regulatory classification and arbitrary keys
are dropped, including nested extras on findings. Model authority cannot override
the fixed envelope. No raw response is forwarded in production summaries.

Free-form model summary and limitations are excluded entirely (approach A),
including affirmative model prose. Product summaries and limitations are
deterministic. Required technical finding observations/recommendations remain
untrusted model-generated engineering suggestions, labeled as such in boundary,
UI, diagnostics and public schema, with reference hints requiring human review.
They are not promoted to legal or organizational facts.

Each batch has its own try/catch, so a failed batch cannot discard later valid
findings or silently authorize a zero-finding conclusion. There is no initial
pass or worst-attainment reduction. Zero successful batches always yield UNKNOWN;
partial findings remain visible. Model uncertainty does not create a fake
high-priority issue. Transport/auth errors remain separate HTTP/tool errors; a
successful HTTP response may include UNKNOWN references.

RAG queries now ask for source-code technical signals relevant to reference
topics. Retrieved context is explicitly informational/untrusted, never operative
law. Context acquisition failure prevents a complete absence conclusion.
Provider/cost `success` is true only for COMPLETE technical execution, regardless
of finding count/severity. A high-priority finding can be execution success;
parser/model failure is execution failure, never framework failure. Estimated
cost calculations and budget defaults are not cleared by this change (LX04/05).

Autofix continues to generate technical patch suggestions from high-priority
findings. Successful generation/application establishes no compliance result;
the UI and application confirmation say so. No fix is automatically applied by
the orchestrator. Quick Fix remains an engineering action.
