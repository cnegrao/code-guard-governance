## Chain model: GLOBAL_INTERLEAVED

The canonical append body at migration lines 132–135 is:

```sql
select entry_hash into v_prev_hash
from gov_repo.governance_ledger
order by entry_sequence desc limit 1 for update skip locked;
if v_prev_hash is null then
  v_prev_hash := encode(digest('CODEGUARD-GENESIS-2026', 'sha256'), 'hex');
end if;
```

`p_organisation_id` is written into the new row but never bounds predecessor
selection. There is one global sequence and one fallback genesis. The digest
concatenates previous hash, event type, subject ID, actor ID, recorded timestamp
and payload. Organisation ID is not itself in that digest expression.
The verifier loops over the global sequence, compares each predecessor hash with
the preceding visited entry hash and recomputes the entry hash.

Concrete sequential example, derived from these bodies (not a new DB execution):

1. Append A1 for ORG_A: predecessor is genesis.
2. Append B1 for ORG_B: predecessor is hash(A1).
3. Append A2 for ORG_A: predecessor is hash(B1).
4. A tenant-filtered walk sees A1 then A2 and compares hash(A1) with hash(B1),
   reporting a mismatch for an otherwise valid global history.

Walking through B1 violates the requested tenant population boundary; ignoring
the predecessor mismatch or recomputing links would fabricate different chain
semantics. A verifier limited to individual row hashes would not prove the
requested tenant chain. No such substitution was implemented.

Search of canonical migrations found the single definitions above, with later
owner/configuration changes and body-digest assertions, not a tenant-local
replacement. Existing repository test sources corroborate the global model:

- `apps/dashboard/tests/postgres-m16/l14-definer-surface-functional.test.ts:24`
  appends different random organisations and expects a global `lag(entry_hash)`
  predecessor relation and three-entry global verification.
- `apps/dashboard/tests/postgres-m16/audit-integrity-read-path.test.ts:27`
  seeds interleaved ORG_A/ORG_B entries and preserves the legacy empty/global
  contract. These existing expectations are not new containment proof.

## Security design and result contract disposition

The required design remains verified principal → explicit organisation →
DB-enforced membership → tenant-bounded verification → typed result → fail-closed
UI. It was not implemented because the historical chain does not support the
assumed tenant-local verification model. No new Authority Policy permission,
generic table endpoint, fallback verifier or service-role authority was added.

Required future vocabulary remains VALID, BROKEN and UNKNOWN, with an explicit
non-positive EMPTY/NO_ENTRIES disposition to be finalized in the architecture
decision. VALID must mean executed verification of the authorized population;
BROKEN must identify an actual integrity failure; missing/unavailable evidence
must remain UNKNOWN or request failure. Authorization denial must fail the
request. Empty means no entries to verify, not positive assurance. These are
requirements, not implemented behavior or an approved revised chain contract.
