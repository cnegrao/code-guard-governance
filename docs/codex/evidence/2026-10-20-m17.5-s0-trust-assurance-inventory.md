Each capability has ID/name, layer/milestone, bounded assertion, implementation
surface, original authority classification, evidence IDs/modes, proof status,
verification IDs and limitations. Each evidence ID resolves to a repository
path, 1-based line, exact anchor, source commit, SHA-256 (UTF-8 with CRLF
normalized to LF), evidence type, classification, mode and execution state.

PROVEN means the **specific bounded assertion** has inspected implementation
and an executed local check at the pinned input. It does not describe the whole
subsystem or a deployment. PARTIALLY_PROVEN records implementation/enforcement
and test sources whose DB integration was not rerun in S0. NOT_PROVEN records a
known proof gap in the inspected scope. UNKNOWN retains unverified context.
An ADR, roadmap intention, workflow file or old PASS statement alone never
establishes PROVEN. Database-enforced means enforcement exists in the migration
chain, not that a hosted database was inspected. Definition locators must be
read in canonical migration order, including the final S7D corrective; they do
not assert that an earlier function body is the final catalog body.

Classification describes the original role: AUTHORITATIVE governance path,
ANALYTICAL derived result, or SUPPORTING evidence/read/presentation. A supporting
read of authoritative facts cannot grant a new authority. No evidence entry is
CI_PROVEN in this S0 audit; the existing M16 workflow configures the independent
PG17 gate but no current CI run was fetched or fabricated.

## 4. Assurance model and evidence lineage

The additive [architecture contract](../../architecture/ADR-GOVIA-TRUST-ASSURANCE-v1.md)
defines Framework, FrameworkVersion and FrameworkRequirement as external reference
metadata; Capability, EvidenceReference, links, requirement mappings,
Applicability and KPIDefinition as projection metadata; AssuranceProjection and
Gap as derived projections; ExternalAttestation as an externally issued artifact
reference; and CommercialClaim as commercial metadata.

Every trace pins exact source versions and scope. Existing evidence, decisions,
authorizations, policy versions and governed states retain ownership in their
current stores. Trust & Assurance never creates new kinds, canonical edges,
L14/L15 facts, policy/control/risk models, evidence stores or permissions.
M16 discovery-evidence support references and M17's closed, tenant-scoped typed
support union provide trustworthy lineage. S0 references those contracts; it
does not widen their unions or treat evidence support as a dependency pin.

Independent axes are applicability, mapping, evidence availability, internal
readiness, external certification/attestation and commercial eligibility. All
vocabularies are closed in the ADR and machine-readable JSON. A mapped,
evidenced requirement with a GAP can remain NOT_ASSERTED externally; no single
compliance status is constructed. UNKNOWN, NOT_EVIDENCED, stale currency and
unavailable access remain distinct. Tenant identity comes from the verified
principal; effective time and recorded cutoff preserve upstream precision.

## 5. Framework source provenance

The seven requested labels are DAMA-DMBOK, EDM Council / DCAM, ISO/IEC 42001,
ISO/IEC 38505-1:2026, ISO/IEC 23894, NIST AI RMF and EU AI Act. These are scope
labels supplied in the task; editions, publisher metadata and legal applicability
have not been independently verified. Each source record is
**EXTERNAL_REQUIREMENT_SOURCE_PENDING**, with an empty requirement list and
unknown version/source metadata. There are no invented clause identifiers,
titles, normative text or satisfaction claims.

Eventual requirements need exact framework/version, publisher, source URI or
licensed reference, source date, identifier/title, section/page, authoritative
source status, reviewer and legally appropriate fingerprint. Existing
TRACEABILITY_MATRIX.md and extension regex mappings do not supply this basis.
Later public NIST/legislation mapping must use authoritative sources; licensed
standards use permitted metadata/references without copying protected text.
This phase performed no external standards research or hosted data access.

## 6. Commercial claims boundary

The ADR requires claim → capability → evidence → framework mapping → current
assurance trace. Factual capabilities can explicitly retain NOT_MAPPED/UNKNOWN
without implying framework alignment. Alignment requires a verified source and
reviewed mapping/evidence; readiness requires scoped sufficiency, current inputs
and no unresolved gaps. Neither is legal compliance or external certification.

CERTIFIED and ATTESTED need verified, current, externally issued artifacts of
the corresponding kind, matching entity/product, edition, scope and dates.
Internal evidence and approvals cannot issue either status. Missing evidence
makes eligibility INELIGIBLE or UNKNOWN. The inspected scanner's tier labels
cannot establish such artifacts. No ISO certification, EU AI Act compliance,
"100% compliant" or "fully governed" claim is eligible from this inventory.

## 7. KPI boundary

The contract defines operational counts only: governed objects with evidence,
unresolved gaps, requirements with evidence, UNKNOWN requirements per axis,
stale evidence references and supporting governed decisions. Each definition
pins tenant/scope, population, deduplication key, predicate, time coordinates,
input versions and missing-data semantics. Incomplete/unavailable queries yield
UNKNOWN, not zero. No percentage, weighting, maturity index or certification
probability is defined; legacy score functions do not implement these KPIs.
